# レビュー指摘の精査

`/code-review` の low / medium / high は、指摘を重複で間引くだけで検証しない。high は再現率を優先するので、不確かな指摘もそのまま出る。そのままでは、PR に載せるかを決められない。報告の直後に、言われる前にこの手順を続ける。

xhigh / max のように検証を含む水準でも、検証が確かめるのは「指摘が事実か」までで、「直す価値があるか」は判定しない。手順2〜3は行い、手順1は検証済みの指摘については、検証の根拠を読み直すだけでよい。

指摘が0件のときと、ユーザーが「ざっと見て」と言ったときは行わない。

## 1. 指摘ごとに裏取りする

指摘1件につき、次の4行を書く。根拠は推測ではなくコードで示し、ファイルと行を添える。

- **到達するか**: 失敗の筋書きの入力・状態に、普段の操作で着くか。上流の入力チェック、DB 制約、呼び出し元、依存ライブラリの実装を辿る。依存ライブラリは手元の版（`deps.edn` や lockfile が指すコミット）を読む
- **すでに扱われていないか**: PR 本文、PR 本文がリンクする設計書、既存のレビュースレッド（`gh api repos/<owner>/<repo>/pulls/<n>/comments`）、同じ変更を先に入れた別製品の PR、呼び出し側、既存のテストで扱われていないか。設計書が「対象外」と決めていれば、その文がどこまでを覆っているかも見る。PR 本文で「扱わない」と明言しているものは、その理由が成り立つかを見る。「消すと黙って変わる」型の指摘は、それを止めるテストがあるかを見る
- **起きたら何が起きるか**: 誰に、何が、どのくらいの頻度で起きるか。元に戻せるか（データの消失、二重の作成、権限の漏れは戻せない）
- **直す費用**: 何行・何リビジョンに手が入るか。設計を変えるか

規約の指摘は、規約の文と、それに反する行を両方引ける場合だけ残す。規約が無い好みの差は落とす。

本番の設定やリソースの有無（テーブルがあるか、権限が反映されたか）のように、コードの外で確かめる前提は、確かめられなければ「未確認」と書き、誰がどう確かめればよいかを添える。確かめられないことを、到達しない理由にも、到達する理由にもしない。

## 2. Fable に独立に判定させる

自分の判定に引きずられないよう、別のエージェントに同じ指摘を判定させる。手順1の結論を待たずに、手順1と並行して出してよい。

- Agent ツールで `model: "fable"`、`subagent_type: "general-purpose"` を指定する
- 依頼文は [fable-brief.md](fable-brief.md) の雛形を埋めて作る
- **渡すのは、対象の場所と指摘の文だけ。** 手順1で書いた結論、自分の見立て、「たぶん誤検知」のような評価は渡さない。渡すと、その見立てが確かめられて返ってくるだけになる
- 指摘が10件以下なら1エージェントにまとめて渡す。11件以上なら10件ずつに分け、複数のエージェントを並行して出す

返ってきた判定も、手順1と同じく根拠のファイルと行を確かめてから使う。

## 3. 突き合わせて決める

指摘ごとに、自分と Fable の判定を並べ、次の3つのどれかに決める。

| 判定 | 基準 |
|---|---|
| 直すべき | 普段の操作で到達し、利用者に見える害がある。または、元に戻せない・権限が漏れる |
| 設計判断しだい | 害はあり得るが、扱うかどうかが仕様の意図で決まり、その意図が PR 本文やコードから読めない |
| 直さなくてよい | 到達しない、すでに扱われている、好みの差、害より直す費用が大きい |

- 両者が一致すれば、そのまま決める
- 食い違えば、双方の根拠の行を開いて決め、決めた理由を1行書く。根拠を見ても決められなければ「設計判断しだい」にする
- 「直すべき」が、PR の今の範囲で直すべきものか、別の PR に回すべきものかも書く

## 4. 報告し直す

- ReportFindings を呼び直す。「直すべき」は `verdict: "CONFIRMED"`、「設計判断しだい」は `verdict: "PLAUSIBLE"` を付け、「直さなくてよい」は外す
- `summary` と `failure_scenario` は、裏取りで分かった事実に合わせて書き直す。重さの順も並べ直す
- 外した指摘は、1件1行で理由を本文に書く（「到達しない: 〜で弾かれる」など）
- 自分と Fable で判定が分かれたものは、両者の見立てと決めた理由を本文に書く
- 「設計判断しだい」は、ユーザーに何を決めてほしいかを問いの形で書く

PR へのコメント投稿や修正は、ユーザーの承認を得てから行う。
