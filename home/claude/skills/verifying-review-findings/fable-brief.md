# Fable への依頼文の雛形

`<...>` を埋めて、Agent ツールの `prompt` に渡す。手順1で書いた結論や、自分の見立ては書き足さない。

---

コードレビューで出た指摘を、それぞれ「本当に直す価値があるか」の観点で独立に判定してほしい。指摘は自動のレビューが再現率を優先して出したもので、誤りや過剰なものが混ざっている前提で読むこと。

## 対象

- 変更: <PR の URL、または jj のリビジョン範囲（例: `jj diff -r 'trunk()..@' --git`）>
- リポジトリ: <作業ディレクトリの絶対パス>
- 依存ライブラリの実装を読む必要があれば: <deps.edn / lockfile の場所、または gh api で読めるリポジトリとコミット>
- 既存のレビュースレッド: <`gh api repos/<owner>/<repo>/pulls/<n>/comments` など。無ければ「なし」>
- 設計書・先行する別製品の PR: <PR 本文のリンク先。無ければ「なし」>

## 指摘

<指摘ごとに、レビューが出した file・line・summary・failure_scenario をそのまま並べる。番号を振る>

## 判定してほしいこと

指摘ごとに、コードを実際に読んで次を答える。推測で答えず、根拠のファイルと行を添えること。

1. 失敗の筋書きに、普段の操作で着くか。着かないなら、どこで弾かれるか
2. PR 本文・既存のスレッド・呼び出し側で、すでに扱われていないか
3. 起きたら、誰に何が起きるか。元に戻せるか
4. 判定: 「直すべき」「設計判断しだい」「直さなくてよい」のどれか。理由を1〜2文で

指摘の言い分に引きずられず、成り立たないと思えば「直さなくてよい」と答えてよい。指摘に無い問題に気付いたら、最後に別に挙げる。

ファイルの編集、コメントの投稿、push はしないこと。
