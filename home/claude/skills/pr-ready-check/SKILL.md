# PR を ready にする前の分割チェック

レビューで「コミットが大きい」「どこから切り出したか読めない」「別 PR に」と言われる前に、自分で見つける。push 済みの draft PR にも使える。

## 1. 対象を列挙する

PR ごとの範囲（stack なら各段の bookmark の間）を出す。

```
jj log -r '<base>..<bookmark>' --reversed --no-graph \
  -T 'change_id.shortest(8) ++ " " ++ description.first_line() ++ "\n"'
```

リビジョンごとの大きさ:

```
jj diff -r <rev> --stat
```

## 2. チェックリスト

各項目を「該当なし／問題あり（リビジョン名）」で判定し、問題ありには分け方の案を添える。

### PR の分け方

- [ ] **別々にリリースされる領域（サーバとクライアント、ライブラリと利用側など）が同じ PR に無い。** 同じ PR にあるときは次の順に判定する。PR 単体で問題がないことは、分けない理由にならない
  1. 片方だけがリリースに入った状態を数え上げ、壊れる状態がないか確かめる
  2. 壊れない順序が 1 つでもあるなら、その順に PR を分ける
  3. どの順序でも壊れるなら分けない。その代わり、同時にリリースする理由とリリース順序の制約を PR 本文に書く
- [ ] **主題に依存しないリファクタが、準備の PR（stack の下の段）に出ている。** 依存が切れなくても stack にして、1 PR のコミット数を減らす
- [ ] **その PR で足した関数がその PR で使われている。** 呼び出し元が後の段にあるなら、本文に呼び出し元の PR を書く
- [ ] **1 PR のコミット数がおおむね 6 以下。** 超えるなら stack の段を分ける

### コミットの分け方

- [ ] **移動・コピー・切り出し・改名のコミットに、挙動の変更が混ざっていない。** 1行目に「移す」「切り出す」「まとめる」「改名」があるコミットを開き、移動先で足した行と移動元で消した行が、import や名前空間の別名の違いを除いてほぼ一致するかを見る。一致しないなら「その場で切り出す（同じファイル内）」→「移すだけ」→「変える」に分ける
- [ ] **1 コミットに、テスト付きの新しい関数が 2 つ以上入っていない。** 実装とテストが離れてスクロールが増える。数え方の例（Clojure）:
  ```
  jj diff -r <rev> --git | grep -E '^\+\((s/)?defn-? |^\+\(t/deftest '
  ```
  1 行で済む補助関数を、それを使う関数と同じコミットに入れるのはよい
- [ ] **1 コミットの差分がおおむね 150 行以内。** テストの量で膨らむときは、機能（作成・更新など）ごとに分けられないかを見る
- [ ] **新しい関数とそのテストが同じコミットにある。** 移動ならテストも同じコミットで動かす。既存の処理にあとからテストを足すだけのコミットは別でよい（本文にそう書く）
- [ ] **1 行目に 2 つ目の対象が出てこない。** 「A と B」「A、B も」と書いているコミットは、たいてい 2 つの論理変更
- [ ] **前のコミットで足したものを、後のコミットで直していない。** 後のコミットで同じ関数を書き換えているなら、前に寄せる（`jj absorb`）か、挙動不変の準備として前に出す。見つけ方:
  ```
  jj log -r '<rev>:: & files("<その関数のファイル>")'
  ```
- [ ] **読む意味の薄いコミット（すぐ打ち消す変更・fixup）が残っていない**
- [ ] **主題と関係ない変更が混ざっていない。** 例: エディタや LSP が自動で書き換えた設定ファイル
  ```
  jj diff -r <rev> --name-only
  ```

### 本文

- [ ] **移動だけのコミットは、本文の読み方とコミットメッセージに「移動だけ」と書いてある**
- [ ] **字下げだけで大きく見えるコミットは、本文で「空白の差を隠して見る」と案内してある**

## 3. 分けすぎない

- 型を細かく増やさない。既存の共通の型に寄せる
- 分けると中間の状態が壊れる（コンパイルできない、権限を見ずに秘密を扱う、入力の型だけ先に緩むなど）なら、その境目では分けない
- CI がコミットごとに lint しないなら、中間のコミットで未使用の private 関数の lint 警告が出るのは、同じ PR の後のコミットで使う限り許容する

## 4. 結果を伝える

問題ありの項目ごとに、リビジョン名・理由・分け方の案を示し、組み直すかをユーザーに確かめる。push 済みのリビジョンを分けるときは、force push してよいかをチームの規則に従って判断する。

## 参考: 読みやすい構成の例

既存の処理を置き換える PR なら、次の順に積むとレビュアーが上から追える。

1. 新しい仕組みの導入（まだ使わない）
2. 新しい仕組みに関数を足す（関数ごとに 1 コミット、テスト付き）
3. 呼び出し元を新しい仕組みに切り替える
4. 旧コードを消す
5. コメントだけの変更
