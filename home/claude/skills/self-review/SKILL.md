# 自己レビュー

未 push のリビジョンを、他人のコードを見るつもりで読む。「書いたときに正しいと思った」ことは根拠にならない。

## 1. 対象を列挙する

```
jj log -r 'remote_bookmarks()..@' --no-graph -T 'change_id.short() ++ " " ++ description.first_line() ++ "\n"'
```

## 2. リビジョンごとに diff を読む

```
jj diff -r <change-id> --git
```

レビュアーが分かっていて（ユーザーの指示、同じスタックの前の PR のレビュアー）、MEMORY.md にその人の基準のメモがあれば、先に開いて手順2〜4の判定に加える。

見るもの:

**実装の妥当性**
- 依頼された範囲を満たしているか。広げすぎ・狭めすぎていないか
- 既存の関数・設定を再実装していないか（同じことをしている箇所を Grep で探す）
- この変更が防ぐ状態に、変更前は本当に到達するか。上流の入力チェック・DB 制約・呼び出し元を辿り、到達する経路と、到達したら何が起きるか（どの層で失敗するか、黙って通るか）を、防ぐ状態1つにつき1行、手順3と同じ Markdown に書く。コミットメッセージに書く帰結は、ここで辿った結果と合わせる
- 壊れやすい前提を持ち込んでいないか（引数リストの手書き、ハードコードしたパス、上流の出力形式への依存）
- 失敗したときにどうなるか。握り潰していないか

**リビジョン規律**
- 1リビジョン = 1論理変更か。「ついでの修正」が混ざっていないか
- 上から順に読めるか。後のリビジョンで前を打ち消していないか
- description はプロジェクトの慣習どおりか
- 別々に切り戻せる領域（サーバとクライアント、ライブラリと利用側）の変更が1つの PR に混ざっていないか。判定は `pr-ready-check` skill の手順に従う

**検証**
- lint / format / テスト / ビルドを実際に走らせたか。走らせていないなら走らせる

## 3. 足したものを1つずつ確かめる

diff を通して読むと、個々の定義やテストの粗さが抜ける。判定の前に、リビジョンが足した単位を書き出す。単位は、定義（関数・型・定数）1つ、テストの `deftest`・`testing` のブロック1つ、コミットメッセージ1本。grep は補助で、`testing` は拾えないので deftest を開いて数える。

```
jj diff -r <change-id> --git | grep -E '^\+\((s/)?def'   # Clojure の例
```

単位ごとに1行書く。中身は「何を見たか」と根拠で、根拠は行番号・件数・条件のどれか（docstring の各文に対応する実装の行、同じ名前の定義の件数、先端での呼び出し元の件数、テストの書き方の多数派の件数など）。根拠を書けない項目は見ていない扱いにする。「このままでよい」「絞れない」「要る」と判断した項目も同じで、根拠（開いた箇所・件数・辿った経路）を書けなければ判断していない扱いにする。✓ や OK だけの行は書かない。

書いたものはリビジョンごとの Markdown に残し、ユーザーが見直しに使えるようにする。置き場所は、記録と同じメインのストア（メインの作業コピーの `.jj/repo`。workspace では `.jj/repo` が指す先）の `self-review/<change-id>.md`。作業コピーの外なので snapshot に入らず、workspace をまたいで共有される。

**定義（関数・型・定数）**
- 要るか。どこから使われるかを、スタックの先端で数える（`jj file show -r <tip> <path> | grep -n <名前>`）。同じ PR の中で使われないなら、呼び出し元の PR を PR 本文に書く
- 引数・戻り値・分岐は使われているか。スタックの先端で、引数は呼び出し元が渡す値の種類、戻り値は受け取って使う呼び出し元の数、分岐はそこを通る呼び出し元の数を書く。値が1種類の引数は固定し、使われない戻り値と、通る呼び出し元が無い分岐は消す。後の PR で使うなら、その PR を PR 本文に書く
- 既存のもので足りないか。同じ働きの関数・テストのヘルパーを Grep で探す
- 名前は中身と合っているか。単数・複数、動詞の選び方を、リポジトリでの使われ方と照らす。同じ名前の定義がリポジトリに無いかも Grep し、あれば中身の違いが docstring から分かるかを見る
- docstring を1文ずつ、それを真にしている実装の行に対応させる。対応する行が無い文は、誤りか不要。主語と目的語を補って言い直せない文（「何を何から見分けるのか」が分からない言い方など）や、遠回しな言い方は直す。呼び出す関数の docstring の言い直しは減らし、この関数が決めることを書く
- 型注釈は、docstring や名前が約束する形と同じ強さか。足した注釈のうち何でも通すもの（Clojure なら `{s/Keyword s/Any}`・`s/Keyword`・`s/Any`。`jj diff -r <change-id> --git | grep -nE '^\+.*:- \[?(\{s/Keyword s/Any\}|s/Keyword|s/Any)'`）を数え、引数と戻り値の1件ずつに、その値を言い表す schema や集合が同じ ns や entity にあるかを書く。あればそれで受ける（集合なら `(apply s/enum 集合)`、docstring が「entity と同じ形」と言うならその形の schema）。無ければ、その値を組み立てている箇所を全部開いてキー（keyword なら取り得る値）を数え、決まっていればその形の schema にする。決まらなくても名前を付けた schema にし、絞れない理由は schema の docstring に書く
- 置き場所（ns）は、使う側と同じか。同じ API を呼ぶ関数などが別の ns にあれば、役割が重ならないかを見る
- 後のリビジョンで docstring や名前が書き換わるなら、途中の段でも正しいか。レビュアーは途中の段を読む

**テスト**
- 各ケースが、関数の約束の1点に対応しているか。対応しないケースは消す
- 名前の主語は、その決まりが要る理由が分かる言い方にする（何とぶつかるのか、何を守るのか）。名前だけで「なぜこのテストが要るか」に答えられないなら書き直す
- 期待値を、テスト対象が中で呼ぶ関数（差し替えていないもの）で作っていないか。作っているなら、テスト対象のどんな書き間違いで落ちるかを1つ書く。挙げられるのが「その関数を呼び忘れる」「結果を渡し忘れる」だけで、その書き間違いが値を使う先（API・DB・schema の検証）で失敗になるなら、配線を確かめているだけなので、約束に対応していても消す。消すときは、その失敗の形（401、schema 違反など）を1行書く。省略しても黙って通る値（省略できるキー、nil でも動く引数）の渡し忘れなら、配線でも残す
- 起こり得ない入力で、本来起きてはいけない結果を固定していないか
- 下の層のテストと同じことを繰り返していないか
- メッセージが、要件でないこと（並び順など）を要件のように書いていないか
- 書き方（定数か文字列か、private 関数の呼び方、「呼ばれないこと」の確かめ方など）は、同じファイルと近いファイルの多数派に合わせる。多数派は件数で確かめる。合わせない理由があるなら、PR のインラインコメントに書く

**コミットメッセージ**
- 変更前の問題が「〜が無かった」だけになっていないか。なぜ要るのか（何がそれを前提にしているか）を書く
- 手順や型の列挙で、docstring やコードを言い直していないか
- PR 番号を書いていないか。PR の間の関係は PR 本文に書く
- 最後の段落の前に空行があるか。行の幅がほかのメッセージと揃っているか

## 4. 追加されたコメントを1つずつ判定する

diff を読む「ついで」では抜ける。リビジョンが追加したコメント行を機械的に列挙してから、1行ずつ可否を決める。

```
jj diff -r <change-id> --git | grep -E '^\+\s*(;;|//|#[^!]|/?\*|<!--|-- )'
```

行コメントしか拾えないので、docstring や関数上の説明文は、そのリビジョンが触った関数を開いて併せて読む。

**このレビュー中に自分が書いたコメントも同じ対象**。指摘を直すついでに足したコメントが一番見落とされる。

判定:

- **残す** — 非自明な現状を理解するのに必要な理由付け（例:「サンドボックスに network が無いため vendor を使う」）
- **消す** — 経緯、旧実装との比較、ベンチマーク数値、選ばなかった選択肢の記録。移し先はコミットメッセージか PR 説明（`pr-inline-comments` skill 参照）

不採用案は否定形で紛れ込む。「〜ではなく」「〜は使えない」「not an option」「instead of」を含む行は、コードだけを読む人に要る情報か、書いた本人の検討過程かを問い直す。

説明の正確さも見る。関数の docstring が失敗時の挙動を書いていない、条件を1つ落としている、といった「嘘ではないが足りない」説明はここで直す。

言語と粒度は既存ファイルの慣習に合わせる。ファイル固有の規約も確認する（例: `home/default.nix` は全エントリに一行説明）。

## 5. 指摘を処理する

直せるものは直す。直さないと決めたものは、なぜ直さないかをユーザーに報告する。黙って見送らない。

ユーザーに直すかを尋ねる指摘には、重みと手間を添える。

- 重み: 「直すべき」（誤り、読み違いのもと）か「任意」（好み、言い回し）か。根拠は前例の件数や、実害が起きる条件で示す
- 手間: 書き換わるリビジョンの数、push 済みか、後のリビジョンで conflict が出そうか

手間に見合わない任意の指摘は、直さない判断を勧めてよい。

指摘にするのは、根拠を件数・行・実害の起きる条件のどれかで示せるものだけ。項目に当てはまるだけで根拠の無いものは「見たが指摘しない」に入れて報告し、直すかを尋ねない。

修正先は `~/.claude/rules/revision-discipline.md` に従う（未 push なら該当リビジョンを直接編集、push 済みなら新しいリビジョンを積む）。

## 6. 記録する

レビューしたリビジョンごとに記録する。所見が空では記録できない。

```
bb ~/.claude/hooks/self-review-gate.bb --mark <change-id> "<一行の所見>"
```

所見には「何を見たか」を書く。手順3の網羅の件数と、手順2の到達の行数（分母は防ぐ状態の数）と、コメント方針の判定結果を含める（例: `defs 3/3 tests 5/5 reach 2/2 msg ok, comment policy checked`。防ぐ状態が無い変更は `reach 0/0`）。件数がそろっていることは、判断の根拠があることを保証しない。件数が diff の単位の数と合わない所見は手順3の列挙を飛ばした印で、コメントに触れていない所見は手順4を飛ばした印。記録は diff のハッシュで照合するので、記録後に内容を変えれば無効になり、再度 mark が必要になる。

## 7. 報告してから push する

レビュー結果を「直した」「見送った（任意）」「見たが指摘しない」の3つに分け、手順3の表のファイルの場所と合わせてユーザーに伝え、push の可否を確認する。記録がないリビジョンを含む push はフックがブロックする。
