# Cross-Project Coding Preferences

## Communication

- 日本語でのコミュニケーションを優先する
- コミットメッセージ・PRの説明・コード中のコメントは、プロジェクトの既存の慣習に従う

## Code Change Principles

- 変更は最小限に保つ。依頼された範囲を超えた「ついでの改善」はしない
- リビジョンは一つの論理的な変更のみを含める
- 既存のコードスタイルとパターンに従う
- 修正は `jj edit` で該当リビジョンを直接編集する（明確な指示がない限り）。ただし push 済みかつ人間レビュアーがいるリビジョンは `jj new` で新規リビジョンを作成する（詳細は `~/.claude/rules/revision-discipline.md`）
- **ファイル編集前に `jj diff --stat` で現在の変更を確認し、無関係な変更を混入させない**
- レビュアーが各リビジョンを独立して理解できるよう分割する。次のリビジョンで消すコードでも、読みやすさのために分けること
- 絶対ホームディレクトリパスをハードコードしない。環境変数や設定変数（Nix なら `config.home.homeDirectory` 等）を使うこと
- 詳細は `~/.claude/rules/revision-discipline.md` 参照

## コメント方針

コメントには**現状の簡潔な説明**を書く。変更の経緯は、理解に必要でない限り残さない。

- 残さない: 旧実装との比較（「〜を置き換える」「旧版と同一」等）、変更理由の物語、ベンチマーク数値、「A ではなく B にした」という選ばなかった選択肢の記録。こうした経緯はコミットメッセージ・PR 説明・インラインレビューコメントに書く（`pr-inline-comments` skill 参照）
- 残してよい: 非自明な現状を理解するのに必要な理由付けを簡潔に（例:「サンドボックスに network が無いため vendor を使う」）
- コメントの言語・粒度は既存ファイルの慣習に合わせる（Communication 節参照）

## Review and Correction Flow

1. 変更を加える前に、対象コードを必ず読んで理解する
2. 変更後は lint/format チェックを実行する
3. エラーがあれば修正する
4. テストが関係する場合は実行して確認する

### コードレビュー指摘への対応

- コードレビューの指摘は1コメント = 1リビジョンで修正する
- 詳細は `~/.claude/rules/revision-discipline.md` 参照

## Error Handling

- エラーが発生した場合、同じ操作を繰り返さず原因を分析する
- ブロックされた場合は代替アプローチを検討し、必要ならユーザーに相談する
