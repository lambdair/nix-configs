# リビジョン規律

## 鉄則: 1リビジョン = 1論理変更

### 編集前の必須チェック

ファイルを Edit/Write する前に、以下を確認すること:
1. `jj diff --stat` で現在のリビジョンの変更を確認
2. `jj log -r @ --no-graph -T description` でリビジョンの目的を確認
3. これから行う変更が既存の変更と同じ論理単位か判断

既に変更があり、これから行う変更が別の論理単位である場合:
→ `jj new -m "目的"` で新しいリビジョンを作成してから編集する

### 同一リビジョンに含めてよい変更

- 同じ機能の実装に必要な変更（実装 + テスト + 型定義など）
- 同じバグの修正に必要な変更
- 同じリファクタリングの一部（関数名変更 + 全呼び出し元の更新）
- 設定変更とそれに直接関連するコード変更

### 別リビジョンにすべき変更

- 異なる機能に関する変更
- 異なるバグの修正
- 「ついでの改善」（近くにある typo 修正、import 整理、フォーマット修正）
- lint/format の修正 → `jj absorb` で適切なリビジョンに配布

### レビュアビリティ優先の分割

原則: レビュアーが各リビジョンを独立して理解できるようにする。

良い分割例:
- リファクタリング（準備）→ 機能追加 → テスト追加
- インターフェース定義 → 実装 → 呼び出し元の更新
- 古いコードの削除 → 新しいコードの追加

たとえ次のリビジョンで消すコードでも、変更の意図が読みやすくなるなら分けること。

### 変更行数による分割の目安

同じ論理変更でも、変更行数が多い場合はレビュアビリティのために分割を検討する。

- 目安: 1リビジョンの変更が概ね150行を超える場合、意味のある単位で分割できないか検討
- 分割例:
  - 大きなリファクタリング → ファイル/モジュール単位で分割
  - 大きな機能追加 → 段階的に分割（型定義 → 実装 → 呼び出し元）
- ただし機械的に行数で切るのではなく、レビュアーが理解しやすい境界で分割する
- 行数が多くても分割すると意味が壊れる場合（自動生成コード、大量のリネーム等）は無理に分割しない

まとめるべき場合:
- 実装とそのテスト（同じ論理変更なら一緒）
- 1行のバグ修正（分割する意味がない）

### コードレビュー指摘への対応

コードレビューのコメントを修正する際は、1コメント = 1リビジョンで対応する。

**手順**:
1. レビューコメントの一覧を把握する
2. 各コメントごとに `jj new -m "fix: コメントの要約"` で新しいリビジョンを作成
3. そのリビジョン内で該当コメントの修正のみを行う
4. 次のコメントの修正に移る前にリビジョンを切り替える

**理由**:
- レビュアーが各修正を個別に確認できる
- 問題がある修正だけを revert/修正できる
- レビューの往復が減る（どのコメントに対応したか明確）

**例外**:
- 同一コメントが複数ファイルにまたがる場合は1リビジョンでよい
- 明らかに関連する複数コメント（例: 同じ関数への指摘）はまとめてよい

### Push済みリビジョンの扱い

push 済みのリビジョンを修正する場合、force push はレビュアーの負担になる。

**編集前の確認手順**:
1. `jj log` で対象リビジョンが push 済み（リモート bookmark あり）か確認
2. push 済みの場合、レビュアーが人間か bot のみか確認

**ルール**:
- push 済み + 人間レビュアーあり → `jj edit` せず `jj new` で新しいリビジョンを作成して修正
- push 済み + bot のみ（copilot, devin 等）→ `jj edit` で直接編集してよい（force push 可）
- 未 push → 従来通り `jj edit` で直接編集
